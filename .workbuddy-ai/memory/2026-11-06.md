# 2026-11-06

## 项目转向：从便签到「可视化组件 + 插件」平台

用户决定推翻现有实现，目标改为多功能桌面视觉组件基础服务，支持插件与第三方服务接入
（对标 foobar2000 的社区生态）。渲染层已定为 WebView。

### 选型结论：Go 宿主 + JS/TS 插件层（不换 Node）

决定性事实：
- **Go 的 `plugin` 包在 Windows 上不存在**：`build mode plugin not supported on windows/amd64`，
  `plugin.Open()` 直接 panic。所以「Go + Go 插件 DLL」这条路从来不可选，无论如何都需要
  一层脚本层或 IPC 层。
- **Node + WebView2 没有成熟框架**：WebView2 只是渲染容器，不带 Node 运行时/IPC/进程模型。
  Go 侧有 Wails v3（2026-10-26 发正式版，要求 Go 1.26+），Rust 侧有 Tauri v2，Node 侧空白，
  退回 Electron 就自带 Chromium 了。
- **Node 宿主 = 两份 V8 堆**（WebView2 的 + Node 的）。
- Node 原生模块（node-gyp / NODE_MODULE_VERSION）是插件生态的定时炸弹，ABI 不稳定。
- 关键：**JS 插件不需要 Node 跑**。Go 可用 goja 跑 JS、wazero 跑 WASM（Rust/Go/C 都能写）。

推荐插件分层：视觉组件（TS/JS，WebView iframe 沙箱）+ 服务插件（独立进程 JSON-RPC 或 WASM）。
真正决定生态成败的是插件 ABI/API 契约的稳定性，不是语言。

### 本次落地：便签窗口改为 WebView2（分支 `feature/webview`，从 main 拉出）

保留 domain / application / infrastructure 三层不动，只重写表现层。

- 依赖：`github.com/jchv/go-webview2`（纯 Go 无 CGO），用底层 `pkg/edge` 而非高层 API
  （高层强制自建 WS_OVERLAPPEDWINDOW，无法无边框/多 WebView）。
- 窗口：自写 Win32 消息循环（`internal/interfaces/webview/window.go`），去掉 walk 依赖。
  exe 从 5.8MB 降到 3.4MB。
- 前端：`web/static/`，原生 HTML/CSS/ES Module，无构建步骤；`web/embed.go` 用内容哈希
  解包到 `%AppData%\StickyNote\web\<hash>\`，旧目录自动清理。
- 资源服务：`SetVirtualHostNameToFolderMapping("app.stickynote", dir, DENY_CORS)`，
  页面源是 `https://app.stickynote/index.html`，拿到正常安全上下文。
- 桥接：JSON-RPC over web message。method: note.get / note.draft / note.save /
  note.setPinned / app.ready / app.close。响应带 `from:"host"` 用于过滤底层库的消息回显。

### 踩过的坑（重要）

1. **首屏空白，必须手动拉伸边框才渲染**：WebView2 控制器创建时 bounds 是 0×0，
   而窗口在此之前已经收到过 `WM_SIZE`，不会再来一次。必须在 `Embed` 返回后主动
   `Resize()` 一次。这是用户报的 bug，已修。
2. **Go 传 JSON 给前端时用的是对象字面量**（`receive({...})`），前端却对它做
   `JSON.parse`，抛异常被 try/catch 静默吞掉，表现为「消息发出去了但回复永远不到」。
   前端 handleMessage 要同时兼容对象与字符串。
3. **`windows` 变量名与 `golang.org/x/sys/windows` 包名冲突**（同一包内），改名
   `windowRegistry`。
4. **`NavigationCompletedCallback` 无返回值**，签名是 `func(sender, args)`。
5. **manifest 只写了 `<dpiAware>true</dpiAware>`（系统级）**，多显示器不同缩放会被
   系统整块位图拉伸。已改为 `true/pm` + `PerMonitorV2`，改完必须用 windres 重新生成
   `rsrc.syso`，否则不生效。
6. **启动阶段 `WM_DPICHANGED` 会把窗口尺寸改掉**：窗口创建在默认位置、再 SetPosition
   挪到目标显示器会触发一次，套用系统建议矩形后尺寸偏离存盘值（525×450 变成 424×413）。
   用 `settled` 标记忽略启动阶段的建议矩形。
7. `go vet` 对 `unsafe.Pointer(uintptr)` 报 possible misuse，加 `lparam()` 辅助函数规避。
8. **本机 Go 代理 `goproxy.io` 不通**，要用 `GOPROXY=https://goproxy.cn,direct`。

### 实现

- 窗口样式 `WS_POPUP | WS_THICKFRAME | WS_MINIMIZEBOX | WS_CLIPCHILDREN`，
  扩展样式 `WS_EX_TOOLWINDOW`（同时移出任务栏与 Alt+Tab）。
- `WM_NCCALCSIZE` 返回 0 → 客户区等于整个窗口，系统标题栏/边框全部消失。
- Win11 圆角显式声明 `DWMWA_WINDOW_CORNER_PREFERENCE(33) = DWMWCP_ROUND(2)`。
- 领域层 `note.New()` 默认 `pinned: true`（含测试同步修改）。
- 前端新增自绘标题栏：状态点 + 标题 + 状态文字 + 置顶/最小化/关闭三个按钮。
  原底部「窗口置顶」复选框与状态栏合并进标题栏。

### 关键坑（比 WebView 迁移时的更隐蔽）

1. **`WM_NCHITTEST` 在 WebView2 下完全失效**。WebView2 的子窗口铺满客户区，
   鼠标命中测试落在子窗口上，宿主的 `WM_NCHITTEST` 永远不会被调用。
   极易误判：直接给宿主 hwnd 发 `SendMessage(WM_NCHITTEST)` 能测出正确结果，
   但那绕过了子窗口路由，真实鼠标输入根本不走这条路。
   **正解**：前端 `mousedown` 判断落点 → `ReleaseCapture()` → 伪造
   `WM_NCLBUTTONDOWN`（`HTCAPTION` / `HTLEFT` …）→ 交给 DefWindowProc 模态循环。
   Electron / Tauri 都是这个路子，好处是 Aero Snap 与贴边吸附保持原生。
   缩放光标因为拿不到系统反馈，改由前端按落点切 CSS 光标。
2. **置顶必须在 `Show()` 之后设**。隐藏窗口上 `SetWindowPos(HWND_TOPMOST)` 的
   Z 序变更会被系统丢掉，`WS_EX_TOPMOST` 位不生效（实测 exstyle 0x180 → 0x188）。
3. **模态循环不能在 COM 回调里直接进**。桥接回调跑在 WebView2 的事件里，
   在里面 `SendMessage` 进嵌套消息循环有重入风险，所以 `BeginDrag`/`BeginResize`
   先 `Window.Post` 排到 UI 线程消息队列。
4. **DPI-unaware 探针读 `GetWindowRect` 会拿到虚拟化坐标**，看起来像窗口自己
   从 525×450 变成了 420×360（正好 ÷1.25），实际是测量误差，不是 bug。
   验证窗口几何要用 PerMonitorV2 的进程，或直接看应用自己的日志。

### 验证方式（无鼠标模拟条件下）

- `exstyle` 位检查：`0x188` = `WS_EX_TOPMOST(0x8)` + `WS_EX_TOOLWINDOW(0x80)`。
- `outer == client`（525×450）证明非客户区被抹平。
- 拖动/缩放只能靠用户实测确认，无法自动验证。

### 修正：任务栏图标要保留（同日 23:21）

最初把「并不会在任务栏显示」理解成需求，用了 `WS_EX_TOOLWINDOW`。用户随后问

**教训**：需求里「不要出现在任务栏」这类描述要当场确认，因为 toolwindow 是单向门，

### 修正二：用户要的其实是托盘图标（同日 23:25）

用户澄清「不是这个菜单栏，是右下角菜单，不是下面那一栏」——要的是**右下角托盘图标**，
不是任务栏按钮。全 git 历史搜索 `Shell_NotifyIcon|systray|tray` 零匹配，
说明这个项目从来没做过托盘，不是「丢了」。

最终形态：`WS_EX_TOOLWINDOW`（任务栏/Alt+Tab 都不占位）+ 托盘图标作为唯一入口。

托盘实现要点（`internal/interfaces/webview/tray.go`）：
- `NOTIFYICONDATAW` x64 下 976 字节，对齐填充必须显式写。cbSize 错一位
  `Shell_NotifyIcon` 返回 false 且**不给任何错误信息**，图标就是不出现。
  `tray_test.go` 用 `unsafe.Offsetof` 把 13 个字段偏移钉死。
- 弹菜单前必须 `SetForegroundWindow`，否则点外面菜单不消失；菜单后补 `WM_NULL` 防残影。
- 进程退出前必须 `NIM_DELETE`，否则留幽灵图标（要鼠标划过才消失）。
- 托盘只暴露 `TrayHooks`（IsPinned/TogglePin/IsVisible/ToggleShow/Quit），
  业务动作留在 App，表现层不反向依赖领域。
- 新增宿主→前端事件 `event{from,event,data}`，前端用 `host:pin` 监听。
  否则托盘改了置顶，标题栏按钮状态会和窗口真实 Z 序漂移。

**流程教训**：这三轮来回（任务栏有→无→托盘）本可以避免。用户第一句
「菜单栏任务图标」用词不精确时，应该直接问「你指的是任务栏按钮还是右下角托盘」，
而不是顺着自己的理解连改两版。

## 追加：下一阶段设计（组件框架，同日 23:56）

用户给出目标：高度自定义的桌面图标框架，JS 插件导入新功能；四类组件（桌面/置顶/悬浮提示/自定义）；

### 关键决策（用户确认）

1. 插件**手动导入**：设置窗口选 zip/目录 → 宿主解包到 staging → 冲突与兼容性检测 →
   落到 `plugins/<id>/` → 注册为停用状态。**不校验签名、不校验版本号**（manifest 无 version 字段）。
2. **只支持指定屏幕**，设置里可细调（记录显示器 ID 而非索引，防热插拔错位）。
3. **提示与日志统一由宿主处理**，组件只能请求不能自己弹。→ 派生：悬浮提示栏不再是独立组件类型，

4. **暂不考虑大量组件并发**，不做 renderer 池复用，每个可见组件一个控制器。
5. **只做技术框架**，不做市场/评级/下载量。

### 架构要点

- 便签也写成插件（`builtin.note`），与第三方同构 → `domain/note` 会被移除，下沉为通用组件状态。
- 窗口只有三条代码路径：desktop（WorkerW 子窗口）/ topmost / toast（WS_EX_TRANSPARENT 点击穿透）。
- 自定义组件不新增窗口路径，由 `customLayer` 声明继承其一。
- v1 只有一种运行时（WebView2），组件逻辑跑在自己的前端 JS 里，不引入 goja/独立进程。
- 所有控制器共享一个 WebView2 Environment，只多 renderer 进程。
- 不做控制器池化；靠休眠（不可见 300s 销毁控制器）省内存。

进程模型、权限矩阵（v1 不给 fs/clipboard，且组件不能开任意窗口）、存储布局、

### 边界收紧：通知归内核，不是组件（同日 00:00 补充）

用户明确：「通知等全局任务不应该做成插件，只应该做在内核之中，所有组件需要通知等
common 行为均通过 API 交由内核处理」。

据此把文档 §3 重写成「内核与组件的职责边界」，判断标准一句话：
**凡是「所有组件都可能要用、且必须统一口径」的进内核，凡是「只有某类组件才需要」的才是组件。**

具体收缩：

- 窗口形态仍三种（desktop / topmost / toast），但 **toast 只有内核能用**。
- 组件类型收敛为三种：`desktop | topmost | custom`，`customLayer` 只能取前两者。
- `customFlags` 只允许 `noActivate`；**`clickThrough` 不给插件**。
  准确的风险不是「看不见」，而是三件事叠加：**盖在最上层 + 用户点不掉 + 可伪装成系统 UI**。
  穿透窗口收不到鼠标事件，所以插件自己画的关闭按钮是死的，用户只能去设置页找是哪个插件再停用。
  （拿不到鼠标事件也意味着做不了钓鱼按钮，是视觉劫持不是交互劫持。）
  同样一个标志，差别在**撤销权归谁**：内核浮层由内核决定消失、受队列与勿扰约束、不覆盖全屏。
- `host.notify` 语义定为「提交一条通知」而非「显示一个窗口」：
  内核可合并、限流、勿扰丢弃，组件无权知道最终呈现形态。
- 设置窗口加第 6 页「通知」（勿扰、时长、停靠位置、按组件统计谁弹得最多）。
  通知既然归内核，就必须给用户一个管住它的地方。
- M1 里**通知服务优先于组件加载**：先跑通内核通知，再谈组件接入。
  顺序反了的话每个组件都会忍不住自己弹浮层，边界破了收不回来。

## WebView2 Composition 最小验证（`experiments/wv2-probe`）

推翻重写前的最后一道验证：把 WebView2 接进 DComp，看页面能不能画在
「置顶层」和「挂 Progman 的桌面层」上，同时保持背景透明与点击穿透。

### 结果：两项全通过

| 项 | 置顶层 | 桌面层（挂 Progman） |
|---|---|---|
| 页面渲染 | ✓ 包围盒 250×150 @ (50,50) | ✓ 同左 |
| 背景透明 | ✓ 方块外变化 0 像素 | ✓ 同左 |
| 点击穿透 | ✓ | ✓ |
| 开销 | 47.6MB / 1 子进程 | 49.4MB / 1 子进程 |

250×150 = 200×120 CSS × 1.25（系统 125%），偏移 50 = 40×1.25，尺寸与位置都精确。

### 踩过的六个坑（都曾让探针静默失败）

1. 必须 `ICoreWebView2Environment3::CreateCoreWebView2CompositionController`；
   用 `CreateCoreWebView2Controller` 会 QI 不到 CompositionController（`E_NOINTERFACE`）。
2. DComp 必须周期 `Commit()`，否则内容完全不出现且无错误码。
3. 必须先 `put_ShouldDetectMonitorScaleChanges(FALSE)` 再设 `put_RasterizationScale`，
   否则导航后被重置成 1.425，页面大 14%。
4. MinGW 8.1 没有 `EventToken.h`（要自备），`WebView2EnvironmentOptions.h` 依赖 WRL（绕开）。
5. GCC 不支持 `__uuidof`，IID 从 `MIDL_INTERFACE("...")` 抄成常量；COM 回调用手写引用计数。
6. 测量坑：抓屏前必须确认自己真在最上层；判透明要排除页面内容区域再比像素。

### 顺带纠正的旧结论

`experiments/dcomp-probe` 第一轮报「挂 Progman 后 DComp 不显示」是**假阴性**——
窗口被浏览器盖住，BitBlt 抓到的是别人的像素。加对照组（同样挂 Progman、纯 GDI 填色）
后确认是遮挡。修正后挂 Progman 的 DComp 内容正常合成，穿透也成立。

## 穿透真正的根因：WebView2 自己的输入窗口（11:55）

一个组件其实是**三个**窗口，只有一个是我们的：

```
StickyNoteHostWindow   我们的宿主（穿透位设在这里）
Chrome_WidgetWin_0     引擎建在宿主下的子窗口
Chrome_WidgetWin_1     引擎在**浏览器进程**里建的顶层"输入窗口" ← 罪魁
```

第三个矩形与宿主重合，样式 `NOACTIVE|LAYERED|TOOLWIN|NOREDIR`、**没有 TRANSPARENT**，
排在宿主与桌面之间，把鼠标全吃了。证据（`diag_cursor.go` 光标探针）：

```
光标探针 "测试弹幕"：命中=Chrome_RenderWidgetHostHWND < Chrome_WidgetWin_1
                     是我们=false 宿主 mousemove=0 nchittest=0
```

宿主的 mousemove / WM_NCHITTEST 都是 0 —— 鼠标压根没到我们的窗口过程。
所以宿主设得再对也没用；这也解释"必须拖一下才穿透、旧位置仍吃鼠标"
（拖动前它一直盖在原位吃，宿主挪走后新位置自然正常）。

**不能删**：DestroyWindow 只能销毁本线程窗口；它还负责键盘焦点/IME/无障碍。
**能做的**：跨进程 `SetWindowLongPtr` 加 `WS_EX_TRANSPARENT`（允许，实测读回生效），
再 `SetWindowPos(SWP_FRAMECHANGED)`。实现 `inputwin.go`：

- 认领判据必须同时有 `LAYERED|NOACTIVATE|NOREDIRECTIONBITMAP` —— 少认一位会误伤
  （实测挑中过一个 `0x00200100` 的瞬时 Chromium 窗口，真正的输入窗口反而漏掉）。
- 两条查找路：① Z 序邻近（矩形完全重合）；② 全屏枚举按矩形重合/重叠。
  置顶窗口（弹幕）的输入窗口**不在置顶层**，Z 序上隔十几层，只能靠②。
- 输入窗口矩形要过一会儿才铺到宿主尺寸（刚导航完是整块内容区）→ OnReady 后
  300ms/1.2s/3s 各重试一次，另外 `refreshLayered`（移动时）也补一次。
- 不能靠 `browserPID`：引擎子窗口 `Chrome_WidgetWin_0` **在本进程里**，拿不到浏览器 pid。

顺带纠正两个错误结论：
1. `WindowFromPoint` / `ChildWindowFromPointEx` 都不是穿透的判据（前者不看透明位，
   后者不看 DWM cloak）。唯一可信是"鼠标消息有没有进窗口过程"。
2. "隐藏状态下挪窗口导致命中区域没登记"这个假设是错的 —— 比对两个实例（拖过 vs 刚启动）
   的矩形/DWM 矩形/exStyle/分层属性/cloak **完全一致**，问题不在窗口状态。

工具：`cmd/winprobe`（Z 序栈 + exStyle + 分层属性 + DWM cloak + `-transparent` 跨进程改样式）。
探针必须 `SetProcessDpiAwarenessContext(-4)`，否则坐标被 125% 虚拟化。

## 组件底色全透明 + 时钟/弹幕的窗口投影（同日，后续）

用户报：① 时钟和弹幕有窗口投影要去掉；② 便签要改成不透明背景。

**根因一：基座样式插在了文档最后，赢过了组件样式表。**
`host.go` 的 `baseCSSScript` 用 `r.appendChild(s)` 把 `<style id="sn-base">` 挂到
`<html>` 末尾 —— 也就是排在组件自己的 `<link>` **后面**。同特异度时后者赢，
于是基座的 `html,body{background:transparent}` 盖掉了组件写的
`body{background:var(--sn-background)}`。日志里四个窗口（含主界面）
`bg=rgba(0,0,0,0)` 就是铁证。修法：插到 `head` 最前面（`insertBefore(s, p.firstChild)`）。
改完 `bg` 立刻变成真值：时钟 `rgb(20,20,22)`、弹幕 `rgb(15,15,18)`。
> 教训：基座样式是兜底，**必须排在最前面**；appendChild 等于"基座优先级最高"。

**根因二：Win11 的 DWM 投影没有单独开关，它跟圆角是同一个属性。**
`DWMWA_WINDOW_CORNER_PREFERENCE(33)`：`ROUND(2)` → DWM 同时给圆角**和一圈投影**；
`DONOTROUND(1)` → 两者一起消失。实测同一条扫描线（弹幕下边缘 y=76）：
改前 31→30→29→28→27→26 的渐变，改后全 31 平值；窗口内部也从"透出投影"变成干净的 `#0F0F12`。
> `DWMWA_NCRENDERING_POLICY(2)=DWMNCRP_DISABLED(1)` **无效**（Set 返回 S_OK 但投影没变，
> 且这个属性不可读，Get 返回 `0x80070057`）。别走这条路。
> 属性 33 是**可读**的，所以能读回断言 —— `createWindow` 里设完就 `DwmGetWindowAttribute` 复核。

顺带修掉的隐性错误：以前所有窗口一律 `DWMWCP_ROUND`，于是 `radius=0` 的时钟和
弹幕被系统偷偷裁成 8px 圆角。现在圆角/投影由 `visual.shadow` 决定
（`WindowOptions.Shadow`：非空 → ROUND，空 → DONOTROUND），形状默认完全交给 CSS。

**便签不透明**：底色从 `body` 挪到 `.note` 上（`html` 透明时 body 的背景会**传播到画布**，
`border-radius` 管不住它，圆角会变成直角），配 `overflow:hidden` 把标题栏裁进圆角。
断言：`.note` 子bg=`rgb(255,251,240)`、子圆角=`12px`。

**工具补强**：`cmd/shot` 加了 DPI 感知（不加则 `GetSystemMetrics` 返回虚拟化的
2048x1152 而不是 2560x1440，坐标换算全错）+ `-px x,y` 点采样；
`cmd/winprobe` 加了 `-dwm <句柄>,<属性>,<值>`（先读→写→读回）。
布局探针加了「子元素/子bg/子圆角」三项 —— 只读 body 会得出"窗口是透明的"的假结论。

**踩到的假读数**：屏幕像素采样前必须确认自己真在最上层。这次桌面被一个最大化的
Chrome（`Chrome_WidgetWin_1` pid 14888 覆盖 -9,-9~2569,1389）盖住，整屏读出来
是 Chrome 的 #141414，跟我们的窗口毫无关系。用 `winprobe -x -y` 先看栈再决定能不能量。

## 「CSS 磨砂就显示磨砂」能不能做到（同日，实测四条路，全部否决）

用户要求：背景必须与 CSS 一致——CSS 写磨砂就磨砂，写透明就透明。

**透明/半透明这条已经成立**：页面 alpha 直通 DComp，CSS 写 `rgba(...)` 窗口就真的半透明，
背后内容原样透出（实测「无材质」时相邻像素差 53.66，背后 Chrome 的文字边缘清晰可见）。

**磨砂这条做不到。** 四条路都试了，判据统一用「同一区域内相邻像素差均值」（模糊会把高频细节抹平）：

| 方案 | 相邻差 | 结论 |
|---|---|---|
| 无材质（基线） | 53.66 | 背后内容原样透出 |
| CSS `backdrop-filter: blur(20px)` | **0.00** | 不是模糊，是**把背后抹成一片纯色** |
| `DWMWA_SYSTEMBACKDROP_TYPE`=2 Mica | 0.00，纯 `#AFAFAF` | 只画系统主题色，不采样背后 |
| 同上 =3 Acrylic | 0.00，纯 `#989898` | 同上 |
| 同上 =4 Tabbed | 0.00，纯 `#A7A7A7` | 同上 |
| `SetWindowCompositionAttribute` acrylic | 51.17（≈基线） | 完全无效 |
| DComp `CreateBackdropBrush` | — | **API 不存在**：`IDCompositionDevice3` 的方法表里没有它，
只有 WinRT `Compositor.CreateBackdropBrush` 有，而它要独占 HWND 的 desktop window target，与 WebView2 冲突 |

关键实验设计（可复用）：**左右对照**。页面左半开 `backdrop-filter`、右半不开，同一帧截图对比，
排除"背后内容在两轮之间变了"这个变量。左半 0.00 / 右半 33.24 —— 结论无可争议。

也测了「是不是 `WS_EX_LAYERED` 挡的」：把弹幕窗口的 LAYERED 位临时清掉再开 acrylic，
结果还是均匀 152，**与分层无关**。所以不是穿透/分层的锅，是 `NOREDIRECTIONBITMAP` + DComp
这条合成路径根本拿不到窗口背后的像素。

**产品结论**：真磨砂只能靠放弃 WebView2 或放弃 DComp，两条都不现实。
CSS 侧可做的是「半透明 + 噪点颗粒」模拟磨砂观感（不需要采样背后），这是唯一可行的近似。

工具补强：`winprobe` 加了 `-accent <句柄>,<state>,<ABGR>`（ACCENT_POLICY）与
`-ex <句柄>,<掩码>,<值>`（读-改-写扩展样式，做样式位对照实验用）。

**关于"位置漂移"的更正**：我一度以为是 bug（弹幕 1270,0 → 599,29、便签 1924,373 → 2017,362）。
用户确认**是他自己在移动窗口**，不是缺陷。以后看到 layout.json 位置变了先问一句，别急着当 bug 查。

## 时钟与弹幕改成透明底

用户要求「时钟和弹幕的样式都改为背景透明」。改的是 **L1 样式包**（不是 L2 覆盖），
理由：`desktop` / `toast` 这两个内置样式本来就是给这两个示例组件定制的窗口形态，
桌面摆件压在壁纸上一块实色底反而多余；L2 的 `visual` 保持空，仍是"用哪个样式"而不是"改样式"。

- `builtin/styles/desktop/style.json`、`builtin/styles/toast/style.json`：`visual.background` → `"transparent"`，
  描述里补一句"底色透明，直接压在壁纸上/浮在下面的窗口上"（样式页会显示这段）。
- `bundles/{clock,danmaku}/style.css`：`:root` 兜底 `--sn-background` 也改成 `transparent`，
  免得单独在浏览器里打开时多出一块黑底。
- 诊断探针加了 `varBg=`（读 `documentElement.style` 上的 `--sn-background` 内联值）：
  **透明底色的组件读 body 也是 `rgba(0,0,0,0)`，跟"基座样式盖掉组件底色"那个老 bug 一模一样**，
  只有把变量本身读出来才能分清"本来就要透明"和"透明是被盖出来的"。

读数（STICKYNOTE_DIAG=1）：
```

布局 danmaku-1：varBg=transparent bg=rgba(0, 0, 0, 0) 子元素=DIV.danmaku  子bg=rgba(0, 0, 0, 0) 子圆角=0px

同步注意：`builtin/` 是 `go:embed`，重编译即可生效；`bundles/` 里改的 CSS **必须手动 cp 到
`bin/data/plugins/components/*/`**，否则跑的还是旧副本（预置包只在首次启动装一次）。

## 布局板按组工作（第二轮）

用户要求「布局也按分组为单位修改（也可以全局修改，不同组用颜色区分）」。
两个澄清回答定死了方向：**选中组之后可以改组内组件位置、其他组不显示**；
**全局 = 显示所有组**。

**设计**：位置是绝对屏幕坐标，摊在一起时"拖的是哪个组"必然含糊，
所以布局板做成两种范围——全部组（只读总览 + 图例）/ 某一个组（只显示它、可拖）。
进组：点侧边栏组头 / 点图例 / 点只读视图里的方块 / 点组头「⋯」进设置；
退出：再点同一个组头，或点「显示全部」。

**改动**
- `Group.Color`（`#rrggbb`，`colorPattern` 校验）+ `GroupView.Color` + `managerGroup.Color` + `groupParams.Color`。
- `componentapp.GroupPalette`（8 色）+ `pickColor()`：取"用得最少"的颜色，
  不按顺序取下一个——删过组之后按顺序会撞上还在用的颜色。
- `ensureGroups` 给没颜色的组补色并落盘（老数据迁移）；`UpdateGroup` 颜色清空时保留原色。
- 前端：`boardScope` 状态（"" = 全部）；组头 `data-act` 从 `groupOpen` 拆成
  `groupFocus`（切范围）+ 齿轮 `groupOpen`（开抽屉）；新增 `.group__dot` / `.main__legend` / `.legend__item`。
- 方块上色走 CSS 变量 `--g` / `--g-soft`（`#rrggbb2e` 淡底），侧边栏色点与图例共用。
  `box--off` 改成虚线 + 降透明度但**保留组色**（原来是把底色洗白，那样看不出哪个组的窗口关着）。
- 只读视图的方块带 `data-act="boxFocus"`，点它进那个组；拖动/双击在 `!boardScope` 时直接 return。

## 第四轮：归属从组件下移到实例

**触发**：用户要求「每个实例单独管理，组件存入独立的组件列表（可以查看和管理下属实例），
同时每个分组内可以通过选择组件新建下层实例，每个实例也可以独立管控所属分组」。

**核心**：`Group.Components` → `Instance.GroupID`。一个组管的是一批**窗口**，不是一批组件——
「两个便签，一个贴桌面、一个浮在最上面」在组件级归属下根本表达不了。

改动：
- `Instance.GroupID` 是唯一真相；`Group.Components` 降级成迁移字段（json 里必须留着，
  删掉等于迁移前先丢数据），`ensureGroups` 搬完就清空。
- **`Boot` 顺序反过来了**：先读实例、再整理分组。归属在实例上，迁移必须先有实例清单。
- `CreateInstance(ctx, componentID, groupID)`（空组→兜底组，兜底组不在就补）、
  `SetInstanceGroup(ctx, instanceID, groupID)`；删掉 `SetComponentGroup` / `groupOf` /
  `groupOfID` / `ComponentsInGroup` / `ErrComponentUngrouped`。
- `DeleteGroup` 的拒绝条件改成"组里还有实例"。
- `rebuild` 的匹配从 componentID 改成 **instanceID**：`rebuildGroup`（整组）+
  `rebuildInstance`（单个）。换组只重建那一个窗口，同组件的另一个实例不受牵连。
- `ComponentView` 去掉 GroupID/GroupName，加 `Singleton`；`InstanceView` 加 GroupID/GroupName。
- `managerState` 多下发一份扁平 `Instances`：侧边栏两个视角、布局板都吃它，
  嵌套那份只给组件设置抽屉。

界面：

  现在 `ComponentView.Singleton` 下发到界面，选组件抽屉里置灰、组件抽屉里"新建"是关的。

## 第五轮：变量（作者声明 / 实例持有）

需求原话：「新增变量，允许作者手动声明需要哪些变量运行程序，同时支持作者设置变量名、说明、
类型（长消息文本框、单行文本框，以及选项模式），同时允许每个实例独立保存各自的变量」。

### 分层
- **声明**：`Definition.Variables []Variable`（`internal/domain/component/variable.go`）。
  `VariableType` = `text` / `textarea` / `select`；`VarOption` 自定义 `UnmarshalJSON`，
  同时接受 `"小"` 与 `{"value":"s","label":"小"}`。上限：32 个变量 / 64KB 单值 / 64 个选项。
- **值**：`component.InstanceVars` 端口（Load/Save/Remove），实现 `persistence.VarsJSON`，
  路径 `data/vars/<组件id>/<实例id>.json`。**和 storage 分开**：storage 是组件写的运行时数据，
  vars 是用户填的配置，混存会被 `setStorage` 盖掉，删实例时也分不清哪些该留。
- **应用层**：`Service.varValues` 内存缓存（Boot 时一次读进，viewOf 不做 IO）；
  `Vars()` 给最终值（默认值兜底），`SetVars()` 三条规则：没提到的不动 / 逐个 `Coerce` /
  未声明的 key 丢掉。**coerce 后等于 default 的不落盘**，空表等于删文件。
- **表现层**：`managerState.components[].variables`（声明）+ `instances[].vars`（值）；
  桥接 `manager.setVars`；`component.ready` 带 `vars`（**现取**，不用建窗快照）；
  改完推 `{from:"host", event:"vars", data:{…}}`，前端 `document.addEventListener("host:vars", …)`。

### 两个顺序/时序坑
1. **变量要在补实例之后读**。原来放在 `ensureGroups` 前面，而首次启动的实例是
   `seedInstances` 才建出来的 → 磁盘上已有的变量文件读不回来。现在挪到 Boot 末尾、
   `SaveLayout` 之前。（`TestSetVarsDropsUndeclaredKeys` 就是靠这条挂出来的。）
2. **打字时不能重渲染抽屉**。`refreshDrawer()` 每次状态推送都重建 DOM，重建就丢焦点与
   光标位置 → "每敲一个字就跳出输入框"。现在检测 `document.activeElement` 是否落在
   `[data-var]` 上，是就跳过这一轮。

### 预置包示例
- `note`：`title`(text) + `fontSize`(select s/m/l/xl → 13/15/18/22px)。
- `danmaku`：`text`(textarea) + `speed`(select slow/normal/fast → 28s/18s/10s)。
  改文字**两份都要改**（无缝循环靠轨道里两份相同文字）。

## 第六轮：列表式变量（`type: "list"`）

### 需求两次调整
1. 先做的是 `type: "json"`：界面给一个 JSON 编辑框，用户直接写 `[{"text":"第一条"}]`，
   落盘 `json.RawMessage` 原样存、原样下发。单测与诊断都通了。
2. 用户随即否决这个 UX：**"不要让用户直接填写 json，解析为填写文本框这样的模式"**。
   选择：一行一条 → `[{"text":"第一条"}]`（字段名在清单里声明，默认 `text`）；
   `json` 类型**彻底移除**。

### 最终形态
- 四种类型：`text` / `textarea` / `select` / **`list`**。
- `list` 在界面上就是**普通多行文本框**，一行一条；空行忽略，每行去首尾空白。
- 落盘与下发是对象数组 `[{"text":"…"}]`——组件拿到的就是真数组，不用 `JSON.parse`。
- 新增清单字段 `item`（只在 `list` 用）：每条落到对象里的字段名，默认 `text`。
- `Coerce` 全空 → 返回 `nil`（"清空这一项"），`SetVars` 删 key、默认值重新生效。
  刻意不返回 `[]`：`[]` 是明确取值，清空输入框是"我不要这个自定义值了"。
- `Normalize` 把默认值归一成对象数组（`["a"]` → `[{"text":"a"}]`），否则
  "用户填的和默认值一样"比不出来（`SameJSON`），默认值会被白白落盘一次。

### 三条踩过的坑
1. **归一不能"顺手把错的丢掉"**。第一版 `Normalize` 里 `listValue(ListLines(default))`
   会把解不出来的项静默删掉（`{"text":"a","color":"red"}` 的 color 直接没了、
   缺字段的项直接消失），`Validate` 再也看不到问题。改成 `listLinesStrict`：
   每一项要么是字符串、要么是**只含 item 字段**的对象，有一项不干净就不归一。
2. **列表项只支持一个字段**，多写的键在加载清单时就报错。理由：用户编辑之后
   只能产出一行文字，多出来的字段迟早会无声消失。
3. 前端那套 JSON 校验（`checkJSONFields` / `is-bad` / `var__badge` / `.input--code`）
   全部删除——界面上没有 JSON 框了，用户在文本框里敲什么都是合法输入。
   一行里出现 `[{` 只是那一行的文字（诊断专门验了这条）。

### 诊断读数（`bin/_diag.exe`，STICKYNOTE_DIAG+DEV，约 22s）
```
实例抽屉(列表变量)：控件=textarea data-list=1 行数=6 初值="" 提示行=2 还有 JSON 框=0
列表已存(界面)：重渲染后="诊断一 诊断二"
弹幕收到列表：正文="诊断一 · 诊断二" 轨道份数=2
方括号当成普通文字：重渲染后="[{\"text\":\"a\"}," 有红框=否
弹幕退回单行文字：正文="这里是水印，乌木啊给您拜年了" 长度=14
推送变量 danmaku-1: map[lines:[{"text":"诊断一"},{"text":"诊断二"}] speed:"slow" text:"…"]
```
`map[lines:[{...}]]` 里没有外层引号 → 是真 JSON 数组，不是字符串。
收尾清空后 `data/vars/danmaku/danmaku-1.json` 与备份**逐字节一致**（lines 键被删，
用户的 text/speed 一个字没动）。

### 顺手做的事
- `MEMORY.md` 超注入上限被截断（6493 字节）→ 压缩到 4481 字节，把引擎/窗口/光标/
  样式的实现级坑拆到新建的 `memory/TRAPS.md`（3215 字节），主文件只留索引与铁律。
- `bundles/danmaku/*` 同步进 `bin/data/plugins/components/danmaku/`（已安装副本）
  与 `bin/bundles/danmaku/`（exe 旁预置包），否则会误判"改了没生效"。

## 第七轮：记录表 `type: "group"`（一条记录多个字段）

### 需求
用户要 `[{title, context}, {title, context}]` 这种"一条记录几个字段"的变量。
原话：**"用纵向的 group 来实现，每个 group 可配置内部属性，同时支持新建 group，
然后根据这些属性回归 json list，同时我希望可以兼容所有常用 json 语法"**。

上一轮我把 `list` 做成了单字段并在加载时**拒绝多字段**，所以这条路当时是堵死的。

### 类型系统铺开
七种类型分两类：
- **标量**：`text` / `textarea` / `select`（字符串）、`number`（数字）、`bool`（布尔）。
  存在的理由是**值保持 JSON 原生类型**——字号存 `13` 不是 `"13"`。
- **集合**：`list`（一条一个字段）、`group`（一条几个字段），都落盘成对象数组。

`group` 的 `fields` 里只能放标量：`list` / `group` 做字段在加载时被拒
（"列表里不能再套列表"）——界面上没法用，组件也会拿到深度不定的值。

### 界面（一条一块的纵向卡片）
- 每张卡片：头部「第 N 条 / 删除」，字段自上而下排（小标题 + 控件），
  底部「+ 添加一条」。
- 容器 `.recs[data-var=…][data-records=1]`，里面输入框带 `data-rec-field` / `data-rec-type`。
- `readVarValues()` 按容器分流：普通控件读 `value`，记录表读卡片拼成 JSON；
  `checkbox` 读 `checked`。
- **空卡片不提交**（点加号只插 DOM，一个字段都没填的卡片在提交时丢掉）。
- 布尔**总是**写 `true`/`false`：`false` 是明确取值，不写就分不清
  "用户关掉了"和"没有这个字段"。
- 加一条 / 删一条走 `data-act="recAdd"` / `"recDel"`；删一条立刻 `saveVars(true)`
  （否则下一次状态推送又把它画回来），加一条不提交。
- 卡片编号靠 DOM 顺序，不存索引；删中间一条后 `renumberRecs()` 往前挪。

### 三个坑
1. **`json.Unmarshal(raw, &json.Number)` 会把 `"3"` 悄悄解成功**——`json.Number`
   底层是字符串，于是"数字字段收到字符串"这种错全漏了。改成 `parseNumber()`：
   先 `json.Valid`（否则 `13px` 会被读成 13 且不报错），再 `UseNumber` 解成
   `any` 断言类型。
2. **`refreshDrawer()` 的焦点保护要认 `data-rec-field`**。原来只认 `data-var`，
   记录表里的输入框带的是前者，漏了就会"每敲一个字卡片重建一次"。
3. **`instanceByID` 不存在**，真正的名字是 `findInstance`。写错之后加一条静默无效，
   只有 `[kernel.manager] error: Uncaught ReferenceError` 在 app.log 里——所以
   `fail()`/UI 异常必须落日志这条铁律又救了一次。

### 诊断读数（临时给 note 的已安装副本挂了个 `cards` 变量，跑完已还原清单）
```
实例抽屉(变量)：控件=3 明细=input/title=便签,select/fontSize=m,div/cards=记录表0条
记录表渲染：卡片=0 加按钮=有 字段= 还有 JSON 框=0
加一条(空)：卡片=1 编号=第 1 条
推送变量 note-1: map[cards:[{"context":"内容二","title":"第二张"}] fontSize:"m" title:"便签"]
记录表已存(界面)：卡片=1 明细=第二张|内容二
推送变量 note-1: map[cards:[] …]
删一条(界面)：卡片=0 明细=
```
要点：加空卡片时**没有**推送（空卡片不落盘）；填完字推送的是真数组
（`map[...]` 里没有外层引号 → 是 JSON 字节不是字符串）；删完退回默认 `[]`。
跑完 `bin/data/vars/note/` 是空的（全部回到默认值，文件被删），note 清单已还原。

## 第八轮：布局板拖边框改尺寸 + 实例内容缩放

### 需求与口径（用户当场确认的两条）
1. 「实例栏里配置缩放」= **内容缩放**（窗口尺寸不变，页面整体按倍数放大），
   不是「窗口等比缩放」。理由是后者和自由拖拽改宽高会互相覆盖，只能二选一。
2. 布局板拖边框**跟随组里的「可缩放」开关**：组里关掉，板子上也不给手柄。

### 关键决策：为什么是两个维度
`Bounds`（窗口多大）和 `Zoom`（里面那页多大）必须分开存。合成一个值就丢掉
「便签拉长但字不放大」这种正当需求。两条都落在**实例**上。

### 实现要点
- **内容缩放用 `RasterizationScale(dpi × zoom)`**，不是 `put_ZoomFactor`。
  后者按 origin 持久化，而所有组件页共用同一个虚拟主机前缀 → 一个实例调过
  缩放会漏到别的实例上。RasterizationScale 是 per-controller 的。
- 新增 `sn_wv2_set_zoom` / `Controller.SetZoom` / `Host.SetZoom`（排 UI 队列）。
- 新增 `Window.SetBounds` / `SetBoundsQuiet`；桥接 `manager.setInstanceBounds`
  （x/y 物理、w/h 逻辑）与 `manager.setInstanceZoom`，都带 `commit`。
- 前端：方块八个手柄（`data-edge`），`resizing` 与 `dragging` 两套状态并行；
  先按「对边固定」夹尺寸再由尺寸反推位置；下限取 `managerInstance.minW/minH`。
- `Instance.Zoom` 的 0 表示「没设置」，`EffectiveZoom()` 归一（0/负数/NaN→1，
  越界夹到 [0.5,3.0]）。放在领域层，因为手改 `layout.json` 是明摆着的用法。

### 一个花掉两轮的坑：`app.js` 是 `<script type="module">`
第一版诊断探针写了 `state.scale`、`findInstance('note-1')`、`call(...)`，
**整段 eval 抛 ReferenceError**，探针一条都没打出来（`evalProbe` 只在 ok 时
打印，回调没回来就静默）。表现是「读数为空」，看着像功能没做。
`openInstanceDrawer` 那次"成功"也是假象——抽屉本来就开着。
**结论：诊断探针只能碰 DOM，或走宿主侧 Go；模块作用域的东西一律取不到。**
（已在 MEMORY.md 里写成铁律。）

另外第一版探针忘了前一步把侧边栏切到了「组件」视角，那里没有 `.group__head`
可点 → 点了个空，读数还是旧组（桌面层，`resizable=false` → `手柄=0`），
差点误判成"手柄没渲染"。

### 诊断读数（第四轮，跑完已把 layout.json 还原）
```

## 第九轮：修「组件还是不能拖拽改大小」

### 症状与真因
用户报"还是不能自由拖拽更改大小比例"。上一轮的诊断只量了「置顶」组（唯一
`resizable=true` 的组），于是得出了"手柄正常"的错误安心感。

真因：**我把两个不同的开关当成了一个**。
- `WindowSpec.Resizable` 语义是"用户能不能**直接拖窗口自己的边框**"。穿透窗口和
  桌面层窗口收不到鼠标，这一位永远是 `false`——三个内置组里桌面层和浮层都是。
- 而我拿它去挡布局板。结果那两个组一个手柄都不给，可**布局板恰恰是它们唯一的
  尺寸入口**（窗口本身拖不动）。

这是上一轮"跟随组里可缩放开关"这个选择的直接后果。那个选择在语义上说得通，
在体验上等于把 2/3 的组废掉了。**改成只看 `sizeMode`**：
`fixed` 才挡（谁都不能改），其余档位都能拖。

### 连带修的三处
1. `manager.setInstanceBounds` 的内核侧校验同步改成只看 `SizeMode`。
2. 组设置里补两条提示，把两个开关的分工写清楚（「可缩放」只管窗口自己的边框，
   「尺寸」档位决定布局板能不能改）。
3. **下限跟当前尺寸取小**：`min(MinBounds, 当前尺寸)`。存盘值本来就小于声明下限时
   （作者改过 manifest / 手改过 layout.json），一夹就等于替用户把窗口放大一截。
   前端和宿主两处都这么改。

另外把 `render()` 的重渲染守卫从 `if (!dragging)` 改成 `if (!dragging && !resizing)`
——改尺寸过程中一次状态推送就会把方块换成新元素。

### 探针本身也错了两次（都值得记）
1. **`focusGroup` 是"再点同一个组就取消"**。板子已经停在桌面层时，探针第一下点击
   把它切回了「全部组」，读出来 `块3 柄0`，差点当成"手柄没渲染"。
   修法：点击前先看 `#boardTitle`，已经是那个组就别点。
2. **`querySelectorAll` 的 NodeList 是静态的**。点一个组头会 `renderSidebar()` 重建
   `#groupList`，旧节点全部脱离文档——对脱离节点 `dispatchEvent` 不会冒泡到
   `document`。修法：每轮循环重新查询。

### 最终读数（第八轮，跑完 layout.json / groups.json 都已还原）
```
布局板手柄(各组)：桌面层(板=桌面层 块1 柄8 可拖) | 置顶(板=置顶 块1 柄8 可拖) | 浮层(板=浮层 块1 柄8 可拖)
布局板手柄(边值)：标题=浮层 边=nw/n/ne/e/se/s/sw/w 光标=nwse-resize
尺寸档位=固定：板=浮层 块1 柄0 提示=说固定
尺寸档位已还原：块1 柄8
```
覆盖了三条分支：三个组都能拖（含两个穿透组）、「固定」该挡就挡且说明原因、
改回「可调」手柄回来。

### 仍然没测
真实鼠标拖手柄的手感（跟手程度、八个方向的命中区、拖到屏幕边缘的夹取）。
合成 MouseEvent 不进拖动逻辑，按老规矩交给用户。

## 第十轮：改尺寸的卡顿/滞后——先量后改

用户报两件事：拖便签边框时内容"一顿一顿"，从布局板拖方块边框时"方块跟手、组件窗口滞后"。

新增 `STICKYNOTE_RESIZE_BENCH=1`（与 `STICKYNOTE_DIAG` 分开，因为后者会改界面状态），
分六段量：只挪位置 / 背靠背吞吐 / 16ms 节奏跟手 / 8ms 高频节流比 / 页面 rAF 出帧 /
页面驱动真实桥接链路（含投递间隔与内容延迟）。

读数（165Hz 屏，scale=1.25）：
- 只挪位置 887µs/帧；改尺寸 1.2~1.4ms/帧；`put_Bounds+Commit` 仅 0.16ms → **贵在 SetWindowPos**
- 页面 240fps；桥接投递 平均 16.0ms 最大 18.9ms（均匀）；内容重排延迟 中位 5ms
- 结论：链路上没有一处能解释肉眼可见的卡顿，剩下怀疑在合成/呈现侧

改动：`SetBoundsQuiet` 几何没变就不发 + 一帧最多一次；`syncContent` 按显示器刷新率节流
（`GetDeviceCaps(VREFRESH)`，夹 6~20ms，**不写死 16ms**）；几何定了强制同步；
被跳过的帧排一次补帧。新增 `needSync` 单测。

顺带修：`postMessage` 必须传对象（传字符串会被当 JSON 字符串值，宿主解析失败）；
`Eval` 不等待 Promise（要取异步结果就挂 `window.__x` 再读）。

数据清理：`layout.json` 里三个实例的 zoom 是之前诊断留下的（2.05/1.7/1.4），
已备份为 `layout.json.bak-diag` 并还原成 1.0。

## 插件分级模型（L1 样式包 / L2 组件）

用户提出：插件是分级的，L1 可以添加「其他样式的窗口」，L2 只能复用 L1 与默认样式的窗口；
便签是 L2，归属「置顶窗口」样式下。

追问后确定的三条：

1. **L1 是纯声明，不是程序**。用户原话「预想中其实只是一个定义规范，也可以用 json 配置
   区域、大小」。所以 L1 = `style.json`，无 HTML、无 JS、不创建 WebView、不占 renderer、
   不需要权限。我一开始推的「L1 自带外壳 HTML + iframe 插槽」被否掉，是对的——
   那会让每窗口多一份 renderer（+50~80MB），而样式本来就只是数据。
2. **L1 与 L2 都可以带样式，L2 默认覆盖 L1**。但覆盖必须分级：
   - 语义字段（`layer` / `activation` / `resizable` / `sizeMode` / `dock` / `titlebar`）
     **锁在 L1，L2 不可覆盖**。理由：L2 若能改 `layer`，分级退化成「每个组件自己声明窗口」，
     §3.2「只有三条窗口路径」也就不成立了。
   - 视觉字段（`padding` / `radius` / `background` / `shadow` / `cssVars`）L2 可覆盖。
3. **依赖失效 → 实例一并停用**。L1 被禁用/卸载时，引用它的 L2 实例窗口销毁、置
   `suspended`、设置页标红「样式缺失」；重新启用后自动恢复。不做静默降级
   （「便签突然换副样子」比「它消失」更让人困惑）。

### 两个我补充的边界

- **L1 管窗口外壳，不管组件内部**。窗口留白/圆角/背景/阴影由 L1 定；
  组件内部布局（标题栏位置、按钮排列、字号）永远归 L2 自己的 HTML/CSS。
  想让便签内部换肤，是 L2 的 `themes`，不是 L1——否则 L1 得懂每个组件的 DOM 结构。
- **L1 表达不了行为**。纯 JSON 只能描述静态模板。要「贴边自动隐藏」这类效果，
  要么内核把该值加进词表（`dock: rightAutoHide`），要么说明它不该是 L1、直接写 L2。
  v1 不提供「L1 带 JS」形态——L1 一旦能跑代码就等于 L2，分级失去意义。

### 文档改动

`docs/component-framework.md` 从 v2 升到 v3（595 行 → 约 600 行）：
- §0 决策表加 6/7/8 三条
- §2 概念模型加「样式包」「ResolvedStyle」，皮肤重新定义为「命名的 cssVars 预设」
- §3.3 重写为「插件分级」（原「组件类型 desktop|topmost|custom」整段删除，
  `customLayer` / `customFlags` 两个字段一并消失）
- 新增 §3.4「样式解析与覆盖规则」（三层合并图 + 语义/视觉字段的覆盖权限划分 + 依赖失效）
- §6 拆成 6.1 L1 样式包 / 6.2 L2 组件包，附窗口词表（6 个字段，只增不改）
- §7 导入流程加「① 识别层级」，校验分两路

### 教训

「一级插件可以添加其他样式的窗口」这句话，我第一反应是按最坏情况理解成
「插件能定义任意窗口形态」，于是推出 iframe 组合 + 双 renderer 的方案。
用户一句「其实只是一个定义规范，也可以用 json 配置」就把方案砍掉一半复杂度。
**遇到「插件能扩展 X」这类描述，先问「扩展的是数据还是代码」**，
这一问能省掉整轮错误设计。

## 第一版内核落地（M0 + M2 部分）

把便签程序改成组件宿主。旧实现整层删除：`domain/note`、`application/noteapp`、
`persistence/json_repository.go`、`web/`（前端搬去 `builtin/components/note/`）。

### 新的分层

```
domain/component/          Style / WindowSpec / Visual / ResolvedStyle / Definition / Instance
application/componentapp/  Catalog / Boot / CreateInstance / Storage 转发
infrastructure/persistence components.json、layout.json、storage/<comp>/<inst>.json
infrastructure/plugin/     Load(root, builtin) + Merge
interfaces/webview/        App（多实例内核）/ Window / Host / Tray
builtin/                   内置样式与组件，go:embed 进 exe
```

### 几个关键实现选择

- **语义字段锁在 L1 靠类型系统，不靠运行时检查**：`Definition.Visual` 里根本没有
  `layer`/`activation` 这些字段，所以组件清单即使写了也无处落地。再在 loader 里
  显式拒绝 `window`/`type`/`customLayer`/`customFlags` 四个键——`json.Unmarshal`
  对未知字段是静默忽略的，不显式拒绝的话用户会以为覆盖生效了。
- **L1 与 L2 的契约是 `--sn-*` CSS 变量**：`--sn-padding/radius/background/shadow`
  由 visual 摊平，其余走 cssVars。组件必须 `var(--sn-xxx)` 消费，样式才生效。
- **样式在文档创建时注入**（`AddScriptToExecuteOnDocumentCreated`），不是页面就绪后
  `Eval`——后者会让首屏先按兜底配色画一遍再跳色，肉眼可见地闪一下。
  注入脚本要处理 `document.documentElement` 还不存在的时刻，失败就等 DOMContentLoaded。
- **托盘挂在一个隐藏的内核窗口上**，不属于任何组件。这样关掉一个组件不会带走整个程序。
  但最后一个实例关掉时主动退出——否则托盘菜单无事可做，用户找不到入口。
- **每个组件一个虚拟主机** `https://<组件id>.stickynote`，`DENY_CORS`。
  组件读不到别人的资源，比同源靠约定隔离可靠。
- **几何口径分开**：X/Y 存物理像素（屏幕坐标本来就是物理的），宽高存逻辑像素。
  换到不同缩放的显示器时只有尺寸需要重新乘。
- **实例带 `Positioned` 标记**：不能靠 `x==0 && y==0` 判断"还没摆过位置"，
  那会把真的放在左上角的窗口每次启动都挪到中间。

### 有意没做的

`layer: desktop`（WorkerW）声明即校验失败——无法在无人值守下验证，宁可不做；
zip 导入流程；通知浮层（`host.notify` 只落日志）；设置窗口。

### 验证

- `go test ./...` 五包全绿：domain（解析规则、id 校验、路径穿越）、persistence
  （三个仓储往返、存储隔离、路径穿越）、plugin（加载、坏包跳过、语义字段拒绝、
  冲突合并）、componentapp（首启建实例、样式缺失、停用保留记录、存储隔离、单例）、
  webview（NOTIFYICONDATAW 布局）
- 实跑：`exstyle` 含 toolwindow+topmost、`outer == client`、旧 `note.json` 迁移成功
  （内容进 storage、几何折回逻辑像素、原文件改名 `.migrated`）
- WebView2 侧 6 个进程 365 MB，其中 renderer 只有 1 个 —— 与"一实例一 renderer"吻合

## 主界面（设置窗口第一版）

用户要求：「只做一个主界面，展示已安装插件和安装插件以及管理插件等能力」。
没有分 8 页，只做「组件 / 样式」两个页签 + 一个安装按钮。

### 最重要的一个判断：主界面不是组件

它管组件，所以不能是组件：
- 若是 L2 组件，用户停用它之后就再也没有入口点回来（循环依赖）。
- 若是 L1 样式，样式是数据，跑不了界面。

所以它和内核通知浮层走同一条边界：**内核自己的能力不能交给被自己管理的东西实现**。
落地：资源放 `builtin/manager/`（与 styles/ components/ 同级，加载器不扫），
没有 `manifest.json`，不绑 L1 样式，桥接命名空间是 `manager.*`，
消息路由用保留实例 id `kernel.manager`。但复用同一套 `Window` / `Host` / `--sn-*` 契约。

### 与组件窗口的唯一差别：占任务栏

`WindowOptions` 新增 `ShowInTaskbar`，为 true 时不加 `WS_EX_TOOLWINDOW`。
组件窗口一律 toolwindow（入口是托盘），但主界面是用户会切走再切回来的，
不占任务栏就找不到了。也因此只有它给「最小化」按钮——
toolwindow 最小化后无法找回，这是老的坑。

### 新分层：安装/卸载放在哪

- 领域：`component.Package` / `PackageKind` + `PackageRepository` 端口
- 基础设施：`plugin.Installer` 实现端口（Inspect / Install / Uninstall / Dir）
- 应用：`Service.InstallPackage` / `UninstallPackage` / `ReloadCatalog`
  —— **守卫、重扫、回滚都在应用层**，因为它要同时看实例、样式引用、注册表
- 表现层只调一个方法，不 import infrastructure（保持依赖单向）

`Service.SetCatalogLoader(func() (Catalog, []error))` 由组合根注入：
应用层不知道插件存在哪、怎么解析。

### 两条硬规则

1. **有实例的组件不能在目录里消失**（`Reload` 拒绝）。实例带着几何与私有数据，
   组件定义一没就成了孤儿——数据还在但界面上找不到。同理，有实例的组件
   它绑定的样式也不能消失。
2. **卸载只删 `plugins\`，不动 `storage\`**。重装回来正文还在；
   彻底清数据是另一件事，不该藏在「卸载」按钮里顺手做掉。

### 安装的四类检测

1. 目录里同时有 `style.json` 与 `manifest.json` → 拒绝（一个包只能一级）
2. id 已存在 → 拒绝（v1 不做覆盖安装）
3. id 用 `builtin.` 前缀 → 拒绝（内置资源每次启动重新解包，覆盖也会被还原）
4. L2 的 `style` 不在目录里 → 拒绝并提示先装那个样式包

复制失败 `RemoveAll` 回滚：半成品会占住 id，用户既装不进去也删不掉。

### 坑

- **选文件夹是模态的**，不能在桥接消息处理里直接弹（COM 回调里进嵌套消息循环）。
  `manager.install` 先回包，再 `Window.Post` 排到 UI 队列执行，结果用事件推回界面。
  和拖动/缩放同一条规矩。
- `SHBrowseForFolderW` 用老 API 而非 `IFileOpenDialog`：一次调用 + 一个结构体，
  不用实现 COM 接口。`BROWSEINFOW` x64 下 64 字节，`ulFlags` 后 4 字节、
  `iImage` 后 4 字节都是对齐填充，必须显式写。
- `managerStyle` 变量名与 `managerStyle` 类型撞车 → 类型改名 `managerStyleView`。
- 主界面也调 `host.log`，但 `onManagerMessage` 起初没实现这个 case，
  自检日志被静默丢弃（id=0 不回包，看不出错）。补上后自检才通。

### 验证（不用截图，靠日志）

前端在 boot 后自检并上报 DOM 数量：
```
[kernel.manager] info: 管理界面就绪：组件 1 个，样式 2 个，实例行 1 行
```
窗口几何：`outer=(643,351) 1200x825 scale=1.250 taskbar=true`（960×660 逻辑 → 物理）。
`ui.json` 落盘 `{x:643,y:351,width:960,height:660}`，下次启动原位置还原。
用户实际操作过拖动、最小化、点安装按钮（日志里有 `window.beginDrag` /
`window.minimize` / `manager.install`），说明界面是通的。

测试新增：`TestInstallUninstallRoundTrip`（真实 Installer + 真实目录扫描，
只把仓储换内存替身，走完 装样式→装组件→守卫拦截→逐个卸载）、
`TestReloadRefusesOrphanInstances`、`TestAllInstancesIncludesDisabled`、
`install_test.go` 七个用例（复制树、重名、缺样式、保留前缀、双清单、卸载边界、路径穿越）。

## 便携模式：数据跟着 exe 走

用户：「我希望用户只需要管理它安装所在的文件夹即可，不要让用户注意到这个文件夹」
（指 `%AppData%\StickyNote`）。

### 决定

数据根目录从 `%AppData%\StickyNote` 改成 `<exe 目录>\data\`。
拷走整个安装目录就是迁移，用户配置目录里不留东西。

```
<安装目录>\StickyNote.exe
<安装目录>\data\{components,layout,ui}.json、storage\、plugins\、cache\、app.log
```

`cache\` 单拎出来装 `builtin\<hash>\` 与 `webview\`：这两块删了不丢数据，
只是下次启动慢一点。混在数据目录里会让用户面对一堆哈希命名的文件夹。

### 写权限判定

不能只看 `MkdirAll`：目录可能建得出来但文件写不进去（只读介质、ACL、受控文件夹访问）。
探针改成**试写一个文件再删**。不可写才退回 AppData 并在日志写明原因。

### 老数据搬迁

只搬 `components.json` / `layout.json` / `ui.json` / `storage` / `plugins`，
**不搬缓存**（会重建，搬 70MB 只是拖慢首次启动）。
搬完 `os.Rename` 旧目录为 `StickyNote.migrated`，不删。
新位置已有 `layout.json` 就跳过，防止每次启动覆盖用户后来的改动。
跨卷 rename 会失败——先复制再改名，所以即使改名失败数据也已经到位，程序照常跑。

### 连带改的界面

- 「打开数据目录」→「打开插件目录」（用户唯一有理由打开的）
- **内置项不再显示「打开目录」**：内置资源住在 `cache\builtin\<hash>\`，
  那个路径不该出现在按钮上；Go 侧 `manager.reveal` 也加了拦截。
- 界面上不再出现"数据目录"概念。

### 验证

实跑：`bin/data` 生成，AppData 的 `StickyNote` 变成 `StickyNote.migrated`，
便签正文 `# 123` 与实例 createdAt 都原样保留，manager 几何回到 643,351。
`cache/webview` 9.2M（新装的，旧的 72M 缓存没搬）。

测试：`migrate_test.go` 三个用例，用 `t.Setenv("APPDATA", tmp)` 把
`os.UserConfigDir()` 指到临时目录，能真实跑一遍搬迁。

## 便签从内核分离，改成预置插件

用户要求：「把便签从内核里分离出来，以插件形式安装」。选项确认：
分发形态 = **独立文件夹随包分发**（接受 exe + 文件夹，不再追求单 exe）；
插件 id = **`note`**。

### 形态

```
<安装目录>\StickyNote.exe
<安装目录>\bundles\note\{manifest.json,index.html,style.css,app.js}   ← 随包分发
<安装目录>\data\plugins\components\note\                              ← 首次启动复制进来
```

`builtin\` 只剩 `styles\`（L1 样式）与 `manager\`（主界面），`go:embed` 改成
`all:styles all:manager`。便签**不再编进 exe**。

### 为什么 id 必须改

`builtin.` 是保留前缀，`Installer.Install` 直接拒绝。便签走插件路径就不能再占它，
否则"谁都不能冒充内置资源"这条界线就破了。改名要动**四处**：
`layout.json` 的 `componentId`、实例 id、`components.json` 的键、
`storage\<组件id>\<实例id>.json` 的目录名与文件名。漏一处不报错，只是正文空了。

`MigrateBuiltinNote` 是幂等整体迁移（layout 里已有 `note` 就返回），
**必须早于 Boot**——Boot 读到指向已消失组件的实例会直接丢弃，那等于删数据。

### 发放账本

`data\bundles.json` = `{"issued":["note"]}`，只增不减。
「发过」≠「装着」：判断要不要装必须看这份记录，不能看"插件目录里有没有"，
否则用户卸载后下次启动又长回来。反过来，已装着但没记账的，只补记录不覆盖文件。

### 首次发放默认启用

没给便签加 `Builtin` 标记（那是"随内核打包"的语义），而是新增
`Service.SetBootstrapEnabled(ids...)`，由组合根在 Boot 前告知。
只对**注册表里没有记录**的 id 生效——用户关掉之后不会被重新打开。

### 启动顺序（两条"必须早于 Boot"）

```
Root → MigrateFromAppData → Materialize(builtin) → scan（只取样式 id，不 Boot）
→ InstallBundles → MarkBundledIssued → MigrateBuiltinNote → Boot
```

- InstallBundles 早于 Boot：否则扫不到便签，Boot 以"没有组件"为前提建不出实例。
- MigrateBuiltinNote 早于 Boot：否则实例被当孤儿丢掉。

`mergeCatalog` 不再自己打日志，改成 `scan`（静默）/ `loadCatalog`（记一行数量）两层，
否则每次启动会出现两行一模一样的"目录载入完成"。

### build.bat

新增 `xcopy bundles bin\bundles /E /I /Y /Q`。漏了这步程序能起来但只有一个空桌面。

### 验证

- 真实旧数据（`bin/data` 里是 `builtin.note`）：日志出现
  `已把便签数据从 builtin.note 迁移到 note`，四处全部改写，正文 `# 123` 保留，
  `bundles.json` 记为 `["note"]`。
- 第二次启动：不重装、不重迁，实例几何原样恢复。
- 临时目录全新安装：装包 → 默认启用 → 自动建 `note-1` → 主界面自动打开。
- 模拟卸载（删插件目录 + 清 layout/enabled）后重启：**没有**重新安装，组件 0 个。

测试新增：`plugin/bundles_test.go`（5 例）、`persistence/migrate_note_test.go`（3 例）、
`componentapp/service_test.go` bootstrap 3 例。`go test ./...` 全绿。

## 修 bug：管理界面开关组件导致整个程序卡死

用户报：「手动在菜单中关闭并打开会导致整个程序完全卡死」。

### 定位手法（可复用）

没有可点的按钮可以自动化，于是**临时**在 `builtin/manager/app.js` 末尾塞一段
自动开关 + 每步 `host.log`，跑一次看日志断在哪：

```
autotest: 开始停用 → manager.setEnabled (id=2) → 停用已回包     ← 没事
autotest: 开始启用 → manager.setEnabled (id=3) → （再无输出，进程还在）
```

结论：**停用能回包，启用必死**。验证完立刻删掉那段临时代码。

### 根因

启用走 `spawnMissing → spawn → Host.Start → edge.Chromium.Embed`，
而 `Embed` 内部是一段 `GetMessage/TranslateMessage/DispatchMessage` 的
**嵌套消息循环**，等控制器就绪才退出。这个回调本身就是在
`DispatchMessageW` 派发进 `ICoreWebView2WebMessageReceivedEventHandler::Invoke`
的——在 WebView2 事件回调里再进一层嵌套循环，撞上运行时内部锁，静默死锁：
没有崩溃、没有日志，进程还活着。

停用的 `DestroyWindow` 同样是在回调里动窗口（同步发 `WM_DESTROY` 到承载
控制器的子窗口），只是实测侥幸没卡。一起挪出回调。

### 修法

`manager.setEnabled` / `createInstance` / `removeInstance` 改两段式：
先回 `{"accepted": true}`，动作排进 `Window.Post`，跑完推 `manager:state`。

## 为此补的两条窗口路径

### desktop：挂 WorkerW

之前 `layer: desktop` 是"声明即校验失败"。真实现只有一条路：成为桌面的子窗口。

```
SendMessageTimeout(Progman, 0x052C) → Explorer 生成壁纸层 WorkerW
EnumWindows                          → 找类名 WorkerW 且**没有** SHELLDLL_DefView 子窗口的那个
SetParent(hwnd, worker)
```

- 挑"空的那个"：带 SHELLDLL_DefView 的是图标宿主，挂上去会盖住桌面图标。
- 找不到就退回 Progman，**这时才** `HWND_BOTTOM` 沉底（否则挡图标）；
  挂空 WorkerW 时**不能**沉底——它下面就是壁纸，沉下去窗口就没了。
  第一次实现无条件沉底、又挂的 Progman，两个错误刚好互相掩盖。
- 坐标系变了：`SetWindowPos` 收父客户坐标，`SetPosition` 里按父窗口原点折算；
  `GetWindowRect` 仍返回屏幕坐标，所以存盘几何不受影响。
- 降级：SetParent 失败 → `HWND_BOTTOM` + `WS_EX_NOACTIVATE`，日志留一行。
- 已知代价：Explorer 重启后 WorkerW 换句柄，挂上去的窗口跟着没，没做重挂。

### toast：穿透写成层级，不写成字段

§3.3 定了"`clickThrough` 不给插件"。又要给弹幕一个穿透形态，于是：

- 词表里**仍然没有** `clickThrough`；
- 新增 `layer: toast`，是唯一带穿透的取值；
- `Style.Validate` 要求 toast 的 id 必须以 `builtin.` 开头 —— 只有内置样式能用。

`builtin.` 前缀本来只是"安装器不许写"的标记，现在多一重含义：**"这条能力只给内核"的凭据**。
常量挪到领域层 `component.ReservedIDPrefix`，安装器与样式校验共用同一个值。

### 顺带修的两个

1. `Show()` 一直用 `SW_SHOW` + `SetForegroundWindow`，noActivate 组件启动那下照样抢焦点。
   改成按语义分叉：`noActivate`/穿透 → `SW_SHOWNOACTIVATE` 且不置前。
2. `dock` 之前只记录不生效。穿透窗口用户拖不动，落位错了就再也回不来，
   所以补 `initialPosition()`：没摆过的按 top/bottom/left/right 贴边，free 居中。

### 布局页

用户要求「在主界面中添加拖拽修改组件位置的界面」。新增第三个页签「布局」：

- 把桌面按比例画成一块板子（`sizeBoard()` 按可用空间等比缩放）；
- 每个实例一个方块，**拖方块就是拖窗口**，双击居中；
- 虚线 = 实例在、窗口不在（隐藏/停用）。

关键决定：

1. **坐标一律物理像素**。`layout.json` 里 x/y 是物理、w/h 是逻辑（故意的），
   后端在 `managerState()` 里把 w/h 乘 scale 换成物理再给前端，
   于是前端只有一套单位，拖拽换算只要一个比值 `screen.w / board.clientWidth`。
   让前端自己乘 scale 的话，125% 下会差一截，100% 机器上永远复现不出来。
2. **拖动中不重渲染**：`render()` 里 `if (!dragging) renderLayout()`，
   否则刚抓起来的节点被换掉，`setPointerCapture` 就断了。
3. **commit 两段**：拖动中 `commit:false` 只挪窗口不写盘，松手 `commit:true` 落一次盘。
   rAF 合并，一帧最多一条消息。
4. **`persistBounds` 末尾 `deferToUI(refreshManager)`**：用户直接拖窗口
   （便签标题栏、时钟表盘）时，布局页方块也要跟着走。这条最容易漏。
5. `manager.moveInstance` 同样走两段式（先回 accepted，再进 UI 队列）——
   `SetPosition` 会同步发 `WM_WINDOWPOSCHANGING`，而我们站在 WebView2 回调里。

## 修两个 bug：桌面组件穿透、页签点不开

### 1. `desktop` 层丢了点击穿透

判定收在一处（`app.go` 的 `spawn`）：

## 穿透还是不行：真正接鼠标的是 WebView2 的子窗口

上一轮只给宿主窗口设了 `WS_EX_TRANSPARENT`，日志里 `transparent=true` 一切正常，
用户点下去依旧毫无反应。原因：**扩展样式不继承**。

WebView2 在宿主窗口里又套了三层：

```

    Chrome_WidgetWin_1

      Intermediate D3D Window
```

`applyClickThrough`：`EnumChildWindows` 把宿主连同**全部子孙**一起加上
`WS_EX_TRANSPARENT | WS_EX_NOACTIVATE`。日志：
`实例 clock-1：已给 3 个窗口设上穿透（宿主 + WebView2 子窗口）`。

导航完成时 `Chrome_RenderWidgetHostHWND` 可能换新的，新窗口不带样式。
所以 `Host.OnReady`（每次导航完成）里再补一次，走 `deferToUI` 排队。

## 迁移 Sciter：可行性验证（结论：三个问题全部通过）

### 验证程序

`cmd/sciterprobe/`（一次性探针，不属于正式程序）+ `internal/infrastructure/sciter/`
（`sciter.go` 是 cgo 指令与 Go 包装，`wrap.cpp` 是唯一接触 Sciter 头文件的地方）。

为什么要一层 `.cpp`：`sciter-x-api.h` 的内联包装用了无名参数（C++ 语法），纯 C 编译不过；
`SCITER_VALUE` 在 C++ 头里是 `sciter::value`（`VALUE` 的派生类），传参要 `reinterpret_cast`。

**cgo 对 `.cpp` 读的是 `CPPFLAGS`/`CXXFLAGS`，不是 `CFLAGS`。** 写在 `CFLAGS` 里
`#include "sciter-x.h"` 直接找不到。

### 结论一：渲染 —— 单窗口、无子 HWND

`SciterCreateWindow(0, &rc, ...)` 建出来类名 `sciter-frame`，`GetWindow(child)` 数出来
**子窗口 0 个**。DOM 求值、布局尺寸、屏幕像素三条都正常：

```
DOM 文本："Sciter OK single window / no child HWND"
视口尺寸：353.6x170.4          ← 460x260 物理 / 1.25 缩放
屏幕像素：平均亮度 38，颜色数 218
```

这是和 WebView2 的根本差别：WebView2 真正接鼠标的是跨进程的
`Chrome_RenderWidgetHostHWND`，改不了它的窗口过程；Sciter 只有我们进程里的一个窗口，
**可以子类化**。

### 结论二：穿透 —— `LAYERED|TRANSPARENT` 可行，`HTTRANSPARENT` 不行

验证方法是自包含的：叠两个自己的窗口（下面一个"接球手"数 `WM_LBUTTONDOWN`，
上面 Sciter），同一坐标 `SendInput` 注入一次真实点击。判定只看**接球手有没有真的收到**
——它就在 Sciter 正下方，只有点击真穿过去才会到它。

| 模式 | 屏幕像素 | 接球手 / Sciter |
|---|---|---|
| 普通窗口 | 38 / 218 | 0 / 1 → 被 Sciter 吃掉 |
| `WS_EX_LAYERED\|WS_EX_TRANSPARENT` + `SetLayeredWindowAttributes(255, LWA_ALPHA)` | **38 / 218** | **1 / 0 → 漏下去了** |
| 子类化 `WM_NCHITTEST` 回 `HTTRANSPARENT` | 38 / 218 | **0 / 0 → 谁都没收到** |

两个要点：

1. **分层窗口不影响 Sciter 绘制**（像素统计和普通窗口一样）。之前看到"亮度 6/颜色 4"
   是因为测试脚本连着跑三个用例，销毁了第一个窗口——见下面第四条，是探针的假象。
2. `HTTRANSPARENT` 不可靠。文档写的是"交给**同线程**下层的窗口"，实测两个同线程窗口
   之间点击被丢弃，谁也没收到。所以穿透**只走分层窗口**这条路。

### 结论三：内存 —— 引擎基线 ~66MB，每实例约 1.9MB

```
 0 个窗口：13 MB       ← 进程刚起，dll 已加载
 1 个窗口：79 MB       ← 引擎 + D3D/D2D 上下文，一次性
 2 个窗口：81 MB
 5 个窗口：87 MB
10 个窗口：96 MB      ← 10 个窗口合计 96MB，单进程
```

对比 WebView2 那套：**611MB / 14 个进程 / 只有 2 个实例**。

### 结论四（坑）：最后一个窗口被销毁 → 渲染后端关闭，之后新建的窗口不绘制

```
销毁后重建（进程里没有别的窗口）：重建的窗口 亮度 7 颜色 22     ← 没画
保留一个常驻窗口再销毁重建：      重建的窗口 亮度 42 颜色 297    ← 正常
销毁两个中的**第一个**再建第三个： 第三个      亮度 40 颜色 254    ← 正常
```

所以触发条件是「**最后一个**窗口被销毁」，不是"第一个"也不是"数量"。产品侧的对策：
进程生命周期内常驻一个隐藏的 keeper 窗口（或永不销毁最后一个），不要让它归零。

### 结论五（坑）：几何必须在**文档加载完之后**设

`SciterCreateWindow` 直接**忽略**传进去的 `frame`，按自己的默认尺寸（800×600 逻辑）居中。
建完立刻 `SetWindowPos` 也没用——`SciterLoadHtml` 触发的那次布局会把它覆盖回去。

顺序必须是：建窗口 → `SciterLoadHtml` → pump 到文档就绪 → `SetWindowPos`。
探针里 `open()` 一开始把 Move 放在 Load 之前，结果两个窗口都叠在屏幕正中
（测量时才发现 A、B 矩形一模一样，等于测了个寂寞）。

### 结论六（坑）：cgo 构建必须带 `-s -w`，否则 Windows 拒绝加载

本机 `go build` 一个 cgo hello-world 直接 `Exec format error`（`ERROR_BAD_EXE_FORMAT`）。
PE 头看着完全正常（PE32+ / machine 0x8664 / subsystem 3），但节区表里前三个节区
的 `VirtualAddress` 是 **`0xffc00000`** —— mingw `ld` 给那些可丢弃的调试节区
写了垃圾 VA，加载器判定非法镜像。

`-ldflags="-s -w"` 之后正常。**正好和项目现有构建参数一致**，但以后若有人为了
调试方便去掉 `-s -w`，程序会变成"双击没反应"，而且错误信息毫无指向性。
